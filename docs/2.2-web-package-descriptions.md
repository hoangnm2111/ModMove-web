# 2.2 Web Application (React)

Figure 3. Web application package diagram

Editable source (draw.io): `docs/web-package-diagram.drawio` — rendered image: `docs/web-package-diagram.png`.

The web client is a single-page application built with **React 18.3**, **TypeScript 5.7**, **Vite 6**, **React Router 6**, **Zustand 5**, **Tailwind CSS 3.4** and **Axios 1.7**. It is organised into five layers; dependencies only point downwards, and `services` is the single package allowed to perform network I/O.

| Layer | Packages |
|-------|----------|
| Presentation | 01 app · 02 routes · 03 layouts · 04 pages |
| Feature & Shared UI | 05 features · 06 components |
| State & Data-binding | 07 hooks · 08 store |
| Data Access & Business Rules | 09 services · 10 domain |
| Shared Kernel | 11 types · constants · config · utils |

## Package descriptions

| No | Package | Description |
|----|---------|-------------|
| 01 | app (src root: `main.tsx`, `App.tsx`, `index.css`, `vite-env.d.ts`) | **Description:** Entry point of the SPA. `main.tsx` mounts `<App />` in `StrictMode` and loads `index.css` (Tailwind directives). `App.tsx` wraps the application in `BrowserRouter`, renders `AppRoutes` together with the global `ToastViewport` and `ConfirmHost`, and imports the `services` barrel once so that side-effect handlers (cancellation refund, wallet settlement) are registered at start-up.<br>**Naming Conventions:** Only `main.tsx` and `App.tsx`; no business logic at this level. |
| 02 | routes | **Description:** Route table and access guards. `AppRoutes` lazy-loads every page with `React.lazy` + `Suspense` and groups routes by role. Guards: `RequireRole` (authenticated + role check, otherwise redirect to `/login?redirect=…`), `GuestOnly` (login/register pages), `GuestOrCustomer` (a guest may fill in a booking draft, GB-28) and `Fallback` (redirect to the role home via `getRoleHomePath`). Both `/login` and `/register` render `LoginPage`; the active tab is derived from the pathname.<br>**Naming Conventions:** A single file `AppRoutes.tsx`; guard components in PascalCase named after the rule (`Require<Rule>`, `<Who>Only`). URLs follow `/<role>/<screen>`, e.g. `/driver/earnings`, `/dispatcher/handled-cases`, `/admin/withdrawals`. |
| 03 | layouts | **Description:** Page frames per role — header, sidebar or bottom tab bar, and an `<Outlet />` for the active page. `DriverLayout` additionally hosts `JobAlertModal` from `features/driver` so a new job offer can interrupt any driver screen.<br>**Naming Conventions:** `<Role>Layout.tsx` exporting `<Role>Layout`: `CustomerLayout`, `DriverLayout`, `DispatcherLayout`, `AdminLayout`. |
| 04 | pages | **Description:** One component per screen (23 in total), grouped by area: `landing` (1), `auth` (1), `account` (1), `customer` (3: Booking, Orders, LiveTracking), `driver` (6: JobList, Home, TripHistory, Incidents, Earnings, Profile), `dispatcher` (4: LiveMap, Incidents, Complaints, HandledCases), `admin` (6: Dashboard, DriverApproval, Users, Withdrawals, Pricing, MasterData). A page composes features and components, reads data through hooks and triggers actions through services; it holds only view state.<br>**Naming Conventions:** `pages/<area>/<Name>Page.tsx` with a named export. Role-specific screens are prefixed with the role (`DriverEarningsPage`, `AdminUsersPage`, `DispatcherHandledCasesPage`). |
| 05 | features | **Description:** Feature-specific UI and logic reused by several pages. `booking/` holds the four-step wizard (`steps/RouteStep`, `CargoStep`, `VehicleStep`, `PaymentStep`) plus `AddressInput`, `FareSummary`, `PolicyModals` (prohibited cargo, warranty policy) and `bookingValidation` (per-step validators). `orders/OrderActionModals` groups the cancel, incident, complaint and rating dialogs; `payment/PayOsModal` renders the PayOS checkout with a countdown; `driver/` provides `JobAlertModal` and the `useAcceptJob` hook.<br>**Naming Conventions:** `features/<feature>/`; components PascalCase `.tsx`, hooks `use<Name>.ts`, pure helpers camelCase `.ts`; wizard steps under `steps/<Name>Step.tsx`. |
| 06 | components | **Description:** Shared presentational components that hold no business state. Top level: `Button`, `Badge`, `RouteMap`, `MapPlaceholder`, `SuspenseOutlet`. Primitives in `components/ui/`: `Field` (labelled input/select/textarea with error and hint), `Modal`, `PhotoUploader`, `StatusBadge`, and `feedback` which exports the `toast` API, `confirm()` and the `Banner` component.<br>**Naming Conventions:** One component per file, PascalCase file name and named export; Tailwind utility classes merged with `clsx` / `tailwind-merge`. |
| 07 | hooks | **Description:** Custom React hooks that bind the UI to data. `useLiveData` subscribes a component to a cache key and re-renders on change, and also exports `useAction` (async action with loading/error state) and `useCountdown` (used by OTP and PayOS timers). `useDomainData` exposes 25 domain-specific hooks (`useCustomerOrders`, `useOrder`, `useAvailableJobs`, `useVehicleTypes`, `useIncidents`, `useOnlineDrivers`, `useHandledCases`, `useCustomerCoupons`, …). `useDriverContext` resolves the signed-in driver profile and active trip.<br>**Naming Conventions:** `use<Name>.ts`; every exported function starts with `use`. |
| 08 | store | **Description:** Client-side state managed with Zustand and persisted to `localStorage`: `useAuthStore` (session, tokens, active role, `signIn` / `logout` / `applyRefreshedTokens`), `useBookingDraftStore` (booking draft kept across wizard steps and across a sign-in redirect), `useDriverStore` (driver UI state such as online/offline).<br>**Naming Conventions:** `use<Name>Store.ts` exporting a hook created with `create<State>()`; derived helpers as plain functions (e.g. `getRoleHomePath`). |
| 09 | services | **Description:** The only package that reaches external data sources. `api.ts` creates the Axios instance `apiClient` (base URL from `VITE_API_BASE_URL`, Bearer-token request interceptor, and a response interceptor that refreshes the access token once on HTTP 401 — concurrent 401s share a single refresh promise — then logs out if the refresh fails) and `toServiceError` which normalises ASP.NET Core *ProblemDetails* into a `ServiceError`. Module services (`auth`, `order`, `catalog`, `case`, `wallet`, `driver`, `map`, `customer-upload`) each expose async `load…` / command methods plus a `subscribe` function. `pagination.ts` mirrors the backend `PagedResult<T>`. `mock/storage.ts` is no longer mock data: it provides the `localStorage` publish–subscribe cache (`readStore`, `writeStore`, `subscribeStore`) that `useLiveData` listens to, together with `ServiceError` and `errorMessage`. `index.ts` is the barrel.<br>**Naming Conventions:** `<module>.service.ts` exporting an object `<module>Service` with verb-noun methods (`orderService.loadOrderTracking`, `catalogService.listCustomerCouponsSync`); errors are always raised as `ServiceError`. |
| 10 | domain | **Description:** Pure business rules — no React, no I/O, fully unit-testable. `pricing` (`calculateFare`, `calculateCommission`, `validateCoupon`), `orderRules` (allowed status transitions `canTransition`, plus `canCustomerCancel`, `refundOnCancel`, `canReviewPickupEvidence`, `canConfirmReceipt`, `canComplain`, `ratingRestriction`, `isActiveOrder`, …), `validators` (phone, e-mail, password, photo file), `vehicleFit.canVehicleCarry` (GB-10 weight and dimension check) and `geo.haversineKm`.<br>**Naming Conventions:** camelCase files named after the rule area; functions are verbs or predicates (`calculate…`, `validate…`, `can…`, `is…`, `has…`). |
| 11 | types / constants / config / utils | **Description:** Shared kernel imported by every other package. `types/` holds the TypeScript interfaces mirroring the backend DTOs (`order.types`, `user.types`, `case.types`). `constants/index.ts` holds display maps (`ORDER_STATUS_CONFIG`, `INCIDENT_TYPE_LABEL`, `REFUND_STATUS_LABEL`, `CARGO_TYPE_OPTIONS`) and `constants/messages.ts` the `MSGxx` catalogue from the SRS, read through the `msg()` helper. `config/business.ts` holds tunable business parameters (`BUSINESS`, `PAYOS_RECEIVER`, `IS_DEMO`). `utils/format.ts` provides `formatCurrency`, `formatDateTime` and `timeAgo`. Static images live outside `src/`, under `public/images`.<br>**Naming Conventions:** `<module>.types.ts` with PascalCase types (`ShippingOrder`, `UserRole`, `OrderStatus`); constants in UPPER_SNAKE_CASE; utilities as camelCase functions. |

## Dependency rules

1. Dependencies point **downwards only**; no package imports a package from a layer above it.
2. `domain` is plain TypeScript and must not import React or any service.
3. Only `services` performs network I/O; pages, features and hooks never call `axios` directly.
4. Data flow: a service calls the API → writes the result into the `localStorage` cache (`writeStore`) → publishes a change event → `useLiveData` re-renders every subscribed component. This keeps several screens showing the same entity consistent without a global data store.
5. The client talks to `ModMove.WebApi` over HTTPS/JSON with a JWT bearer token; real-time order tracking is served by the SignalR hub `/hubs/tracking`.
